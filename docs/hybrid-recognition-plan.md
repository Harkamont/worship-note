# 하이브리드 악보 인식 개선 계획

**목표:** 사용자가 제공한 PNG/JPG에서 음표·리듬은 전용 OMR, 코드·가사는 별도 OCR/AI로 읽어 정확도와 교정 부담을 개선한다.

**승인 범위:** 사용자가 2026-10-18 전용 악보 인식과 AI를 조합하는 개선 시험을 요청했다. 기존 단선율·편집·전조·PNG/TXT 출력 범위를 유지한다.

## 설계와 선택

기존 전체 이미지→범용 AI 방식은 저가 모델과 Sol에서도 실제 24마디 악보의 마디·리듬을 잘못 읽었다. Sol의 줄별 인식은 부분 개선됐으나 모든 줄이 정확하지 않았다. 다음 방법을 우선한다.

1. Audiveris를 별도 로컬 프로세스로 실행하여 오선·음높이·음가·붙임줄을 MusicXML로 받는다. 원본과 확대본을 동일 조건에서 비교하고, 내용은 자동 수정하지 않는다.
2. MusicXML의 음악 데이터와 좌표를 이용해 마디 순서를 고정한다. 코드·가사는 한국어 OCR과 AI가 해당 마디 안에서만 보완하도록 한다. AI가 OMR 음표를 임의로 다시 쓰지 않는다.
3. 데이터 검증과 원본 대조 결과를 각각 기록한다. 모호한 리듬·음표를 경고하며, 지원하지 않는 성부·셋잇단음표를 조용히 삭제하거나 채우지 않는다.

전용 엔진은 별도 실행 파일로 유지한다. 현재 원격 Worker에는 Java가 없어 로컬 실행과 원격 게시를 구분해야 한다. 엔진 시험이 개선을 보인 뒤 적합한 실행 경로만 앱에 연결한다.

## 실행 순서

- [x] 공식 Audiveris Mac ARM 번들과 한국어·영어 OCR 데이터를 작업 폴더에 준비하고 해시를 확인한다.
- [x] 원본 600×927 PNG를 변환하고 처리 시간·마디·음표·리듬·코드·가사를 추출한다. 원본은 오선 간격 8px로 거절됐다.
- [x] 내용 변경 없는 2배·3배 확대 조건을 비교한다. 곡 분리 설정과 텍스트 마스킹도 별도 조건으로 시험했다.
- [x] 원본의 24마디·48코드와 수동 판독한 이벤트를 대조한다. 기존 AI 결과와 같은 기준으로 비교한다.
- [x] 개선된 결과로 MusicXML/MXL→Score 변환을 실패 테스트부터 구현한다. 쉼표·임시표·붙임줄·점·박자·코드·가사·불완전 마디·다성부를 검사한다.
- [x] 로컬 인식과 앱의 편집·전조·PNG/TXT 내보내기를 실제 이미지로 연결해 확인한다. 불확실한 부분은 사용자에게 표시한다.
- [ ] 테스트·타입 검사·린트·빌드와 독립 리뷰 후 현재 게시 방식에 맞는 소스와 실행 설정을 반영한다.

## 실행에서 확인한 사항

- Audiveris 5.11.0 공식 Mac ARM 번들과 포함된 Java를 사용하며, 사용자 홈 대신 작업 폴더에 설정을 보관한다. 한국어 OCR의 보조 중국어 모델도 같은 버전 데이터로 보완한다.
- 2배 확대와 곡 분리 비활성화 조건에서 24마디·109개 이벤트를 출력했다. 수동 판독 기준은 24마디·114개 이벤트(음표 104개, 쉼표 10개)다. 개수 일치만으로 정확도를 판단하지 않는다.
- 3배 확대는 23마디로 잘못 합쳤다. 오선 바깥을 가린 실험도 23마디였고 일부 줄기 끝을 잘라 운영 방식으로 채택하지 않는다.
- Worker는 Java/Python 실행을 지원하지 않는다. 게시 사이트는 MusicXML/MXL 가져오기와 코드·가사 보완을 제공한다. 로컬 앱은 별도 HOMR Companion으로 이미지에서 전용 인식을 실행한다. 게시 사이트의 전용 이미지 인식까지 작동한다고 표시하지 않는다.
- OMR 원시 데이터와 줄별 원본을 저가 AI에 제공하는 별도 실험을 진행한다. 수동 정답은 프롬프트에 넣지 않는다. 리듬 오류를 쉼표로 채워 통과시키지 않는다.
- 검증용 24마디 수동 입력본은 자동 인식 결과와 구분해 저장한다.

## 추가 비교와 채택 방향

Audiveris보다 다른 전용 엔진 HOMR가 이 표본에서 더 정확했다. PyPI 0.7.0과 공식 저장소 최신 소스를 각각 실제 실행했다. 원본 PNG를 그대로 읽었으며 수동 정답을 엔진에 제공하지 않았다.

| 출력 | 음높이·쉼표 종류 | 음높이+음가 | 명시적 붙임줄 | 마디 수 |
|---|---:|---:|---:|---:|
| Qwen3.8 전체 이미지 | 별도 보고서 | 69/114 | 별도 보고서 | 24 |
| Audiveris 2배 확대 | 별도 보고서 | 88/114 | 5/14 | 24 |
| HOMR 0.7.0 | 114/114 | 105/114 | 0/14 (동음 슬러로 기록) | 24 |
| HOMR 공식 commit ab369ac54277afab582afa4725441f7cbba76593 | 114/114 | 112/114 | 14/14 | 24 |

최신 HOMR는 24마디가 모두 4박이고, 원본과 다른 길이는 14마디 앞 두 음이다. 원본의 점8분+16분을 8분+8분으로 읽었다. 원본에 없는 장식 기호 4개와 잘못된 제목도 별도 오류다. 코드·가사는 출력하지 않으므로 전체 악보 정확도가 98.2%라는 뜻으로 일반화하지 않는다. 같은 입력 재실행은 4.258초이며 XML SHA256이 같았다. 다운로드를 마친 뒤의 로컬 실행 시간이고 추론 API 비용은 0달러다. 서버·전기 비용은 포함하지 않는다.

Audiveris의 힌트와 원본을 Qwen3.8에 다시 제공해 7줄을 모두 읽는 방식은 7/7 검증 실패, 총 $0.009609868였다. 이를 운영 경로로 채택하지 않는다. 대신 HOMR의 음표를 고정하고 AI가 코드·가사만 반환하도록 구현한다. 서버에서 고정된 마디·음표 수를 확인하고 음악 데이터는 그대로 보존한다.

## 실제 앱 연결

로컬 Companion을 127.0.0.1:3101에 별도 실행한다. Worker가 같은 사이트의 이미지 요청을 인증 토큰과 함께 전달하고, Companion은 고정된 Python 가상환경과 HOMR 모듈을 작업 폴더에서 실행한다. 10MiB 입력·2MiB 출력·한 번에 한 작업·60초 실행 제한과 임시 파일 정리를 적용했다. UI의 원본 PNG 인식은 4.8초에 성공했다. Worker에서 `redirect: error`는 실제 미지원이어서 `manual`과 상태 검사로 바꿨다. 토큰을 리다이렉트로 전달하지 않는다.

코드·가사 보완에서 Sol standard는 병합에 성공했으나 마디+박+기호 41/47이었다. 더 저렴한 Flex 첫 호출은 인접 두 코드를 합친 잘못된 기호로 실패했다. 단일 코드 문법을 schema로 제한하고 인접 기호를 별도 객체로 읽도록 지시한 후, 한 번의 Flex 재시험에서 가사 114/114·코드 기호+마디 48/48·확정 마디+박+기호 43/47을 확인했다. 비용 $0.012253·11.191초이며, 형식 통과만으로 원본 일치를 추정하지 않고 수동 기준으로 각각 비교했다. 이 표본의 실패를 보고 조정했으므로 다른 악보에 대한 검증으로 간주하지 않는다.

## 검증 기준

최종 로컬 UI에서 한 번의 원본 업로드→HOMR→Sol Flex 병합을 확인했다. 16.257초, API $0.0063858(입력 5,131 중 캐시 5,128토큰)이다. 자동 결과는 음가 포함 112/114, 가사 값 114/114, 코드 기호+마디 48/48, 확정 코드 박 45/47이다. 독립 검산으로 확인했다. UI에서 음가 두 개와 코드 박 두 개를 고친 프로젝트는 114/114·47/47이며, 원본·인식 정보와 수동 교정 내역을 함께 보관했다. A→G→A 전조와 3마디/줄 PNG, JSON, 가사 TXT를 실제 다운로드했다. 띄어쓰기·문장 구분, 미확정 16마디 E의 박, 기본 템포·구간·송폼, 지원하지 않는 슬러는 별도 검토 대상이다.

실행 성공, XML 생성, Score 검증 통과, 원본 일치 여부는 별개다. 24마디 보존 여부와 확인한 음표의 음높이·음가·점·붙임줄, 48개 코드의 기호·박 위치, 가사의 음절·음표 연결을 비교한다. 전수 확인하지 않은 항목에 전체 정확도 수치를 붙이지 않는다. 외부 추론 API 비용과 로컬 CPU 처리시간도 구분한다.
